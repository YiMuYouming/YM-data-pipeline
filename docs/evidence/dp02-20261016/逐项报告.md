## 分类汇总

三类是事实性质：**管道缺陷**包括数据接入契约的调用侧缺陷，但同时标清所有者；
**供应商限制**包括数据尚未提供、时点不可验证和暂态响应；**合法空**只表示业务
窗口/对象没有行，不表示源报错。对没有保留的具体异常不强行补结论。

| 项 | 分类与根因 | 本单处理 |
|---|---|---|
| market_limit_state 502 | 接入契约缺陷：GET 字符串 True 未解码，归轻舟网关 | 离线重现并给 handoff-gateway.patch；未修改目标仓库 |
| market_limit_state TIMEOUT/慢 | 供应商延迟，叠加原有串行请求/空池复读；失败耗时只记最后一跳是管道缺陷 | 修复累计失败耗时；保留 TIMEOUT，不新增重试/并发 |
| include_promotion 请求 | 管道缺陷：校验层转成 previous_date 后，StockToday 仍只认 include_promotion | 已修并经公共 API 离线 RED→GREEN |
| intraday 11–14 秒、industry 空 | 供应商请求耗时和辅助日表无行；管道诊断不够细 | 增加分批耗时、辅助表行数/状态/码；不编造 industry，不宣称延迟已消除 |

| daily_basic 空 | 合法空：同源 suspend_d 确认 600825 在 10-15 停牌 | 记录正向停牌证据，不用快照市值或其他网页补值 |

## 1. market_limit_state：三种问题不能合并

历史 `market_limit_state-0-record.json` 的 502 diagnostics.detail 明确写
`market_limit_state include_promotion must be boolean`；这不是 StockToday HTTP 502。
网关 values 从 GET 参数取出后仍为字符串，而公共 `_validate_params` 严格只收 bool。
由源代码内存副本离线重放：原网关 502，建议补丁 200 且管道收到 bool；重复值 400。
完整过程与边界见 cross-repo-handoff.md / cross-repo-proof.json。严格 bool gate 未放宽。

另一份 09:30 历史 record 是真实 TIMEOUT，最后上游耗时 15423ms，总请求约 21 秒。
当前只读 label `limit` / `promotion` 分别 5640 / 5297ms，皆 empty：每轮 9 次
limit_list_d（U/D/Z 各三次已有空复读）+1 次 limit_step，HTTP 200/code 0/0 行。
这里不能推断市场没有涨跌停；同轮实时快照有 61 只涨停，日表未供数据归供应商限制。
本轮没重现网络超时，不把过去的超时判成已修。

确认两个管道缺陷并修复：

1. `_call_limit_state` 失败时直接 return 最后一份 outcome，漏记前序子请求；现在
   用整个复合请求起点计时，仍保留原 timeout/auth/质量码。离线 fake clock 验证
   最后一次 1000ms、累计 6000ms，见 red-valid 与 green-final。
2. 公共入口 `include_promotion=True` 会 pop 开关并设置前一交易日 previous_date，
   适配器原来只检查已被 pop 的开关，可能成功返回却漏掉 promotion。现在兼容消费
   已校验 previous_date，确实取当前/前日再调用既有 derive_limit_promotion。
   `test_canonical_promotion_uses_normalized_previous_date` 从只调 10-16 的 RED 到确实
   调 10-15 的 GREEN。未更改晋级公式、provider、交易日算法或门禁。

## 2. market_intraday_state：耗时与空行业

原 09:30/10:00/11:54 成功样本的 attempt 分别 12654 / 10857 / 14131ms，且已有
`limit_up_metadata_incomplete`。新的 label intraday 30356ms：4 个 rt_k wire 请求
耗时 10202、11930、3722、1537ms，合计 27391ms；辅助 limit_list_d 2538ms，
固定结构性缺口腾讯补值约 270ms，剩余为解析、校验与本地计算。
这里已定位到上游请求是主要成本，不伪报某个 Python 公式是瓶颈。

源上实时快照只提供报价；industry/seal_time 从同一 StockToday 的日表
limit_list_d(U) 补元数据。该辅助请求本轮 HTTP 200/0 行，所以 61/61 industry 为空。
没有把其他来源的行业硬拼进来。生产元数据观察新增：

- observation.batches[].latency_ms，保持每个批次原耗时。
- observation.limit_metadata 的 status/error_code/returned_count/matched_count/latency_ms。
- source_gaps 增加 limit_up_metadata_empty（源空）或 limit_up_metadata_unavailable
  （源错/日期代码不匹配），并保留原完整性 gap。

修后第二次读查仍用了 27860ms，不能宣称提速；其中创业板一个 rt_k 请求就用了
14454ms。辅助元数据返回 empty/EMPTY_UPSTREAM/0 行/549ms，诊断已可定位。
测试 `test_limit_metadata_reports_missing_rows_without_filling_industry` 与
`test_intraday_public_observation_keeps_batch_and_metadata_details` 有 RED→GREEN。

后续优化建议仅方案：由一个生产者共享同轮全市场结果，按共享账号预算评估有界
并发或供应商批量接口；辅助日表增加有界、显式时效的发布状态观察。未做跨轮陈旧
缓存冒充新值、源切换、新增重试或取消覆盖/时效校验。

## 3. sector_index：缺时点、缺名称与暂态不可解析

历史 `sector_index-1-payload.json` 中文化传媒能匹配 881164，出版传媒 missing；
另一个历史样本军工 missing。`出版` 在源上没有精确匹配，属于合法空选择，不能
自动把出版子行业当成整个文化传媒，或把宽泛军工词绑成某个细行业。

同花顺摘要没有可信行情时间，代码也不能从接收时间倒推行情时间；null 本身忠实，
但没有原因的 success 容易让下游误解。已改为 degraded + DATA_TIME_UNKNOWN，
保持 data_as_of=null / freshness unknown，不填 now、不造 timestamp。
离线按原信封数据与原 effective params 重放，文化传媒行保留、missing 保留、原因补齐。

本轮前两次在线查询 HTTP 200 却没有可解析表，保留 PARSE_FAILED；没有原始 HTML
body，不能断言是反爬、临时响应还是某个页面分支。第三次修后查询原多名称参数，
473ms 正常返回部分行、degraded，原因包含原覆盖缺口和 DATA_TIME_UNKNOWN。
这个恢复不被写成“修复了供应商可达性”。三次在线达到本项上限，没有继续刷请求。

## 4. index_intraday_compare：盘初合法空和已有时段的事实时间

09:30 历史失败参数未给 period，默认 15m；源先把分时组装到 09:45，再按 now 排除
尚未完成时段，得到空，原 builder 一律归 INCOMPLETE_INDEX_COMPARE。当天首个窗口
前本来就没有完成数据；修复先返回 items=[] / NO_COMPLETED_INTRADAY_BARS，不访问
上游，quality empty / returned_count=0。5m 与 60m 相应为 09:35 / 10:30。
不能拿尚未完成 bar 供门禁使用。窗口之后真实 source error / incomplete 仍 error，
保留对照测试 `test_after_opening_missing_provider_is_still_error`。

11:54 原成功 compare 的 data_as_of 仍 null，是 `_data_as_of` 没有处理本意图，
尽管业务行含 trade_date 与 t。现取三指数共有的最后完成 bar，忽略“累计”，没有
共同时间则不补造。新读查 compare-fixed 为 824ms、data_as_of=2026-10-16T15:00:00+08:00。
不把 after-close 成功当成 09:30 供应商在线证明。

RED 证据：开盘空窗口、原 envelope 空质量、共同时间、不同指数时间不交齐等分别
在 red-valid / compare-red-valid / red-empty-quality / red-common-time 中。
首次 compare 测试夹具遗漏 legacy 必填字段，先被既有 QUALITY_COMPARE_INCOMPLETE
拒绝；已补成完整夹具，并用 ee95566 的原 `_data_as_of` 在隔离命名空间再次跑出
真实 missing timestamp RED，没有删除或放宽质量门。

## 5. daily_basic 与停牌 K 线

按原参数 daily_basic(600825.SH, 20261015, max_rows=1) 返回 HTTP 200/code 0/空表；
追加一次同源 public suspend_d(600825.SH,20261015)，明确返回 suspend_type=S。
因此空日指标有正向停牌证据，不归权限错误；不转其他来源补市值/换手率。
证据为 online-basic / online-suspension-diagnostic，未自动在每次查询增加停牌请求。

清单中的 601811 与 301041 原 K 线数据时间其实是 10-15、fresh。真正缺解释的
样本是 trial index 中的 600825（stock_kline-2），原 effective params 还有
adjustment=qfq / use_case=agent，最后日线 10-12，却是 status success、freshness stale、
reason_codes=[]。已修默认日 K 的日期落后解释，附 expected_trade_date、last_bar_trade_date、
BAR_TRADE_DATE_LAG，并降级。不把“日期落后”一律写成停牌；本轮只能确认 10-15 停牌，
不扩写 10-13/14 的未查证状态。显式历史 end_date 仍 historical。

原始数据离线重放维持 10-12 日线和 stale，补上解释；当前收盘后 600825 新读查
已出现 10-16 bar，不能反向改写盘中事实。重放第一次误用 record 的原始参数，而
没有使用 payload 绑定的 qfq effective params，被复权质量门拒绝；修正后重放通过，
失败原件保留，未改动任何原始 result 数据。
